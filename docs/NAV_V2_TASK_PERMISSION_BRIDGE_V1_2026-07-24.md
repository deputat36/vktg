# Navigator v2 — мост серверных разрешений задач

## Проблема

После включения lifecycle `open → in_progress → результат → done` production оставался в состоянии:

- 98 задач;
- 88 задач `open`;
- 0 задач `in_progress`;
- 0 задач `done`;
- 0 событий `task_status_changed`.

Read-only проверка действующих функций показала конкретный разрыв:

1. `nav_v2_get_deal_card` возвращает для каждой задачи авторитетный `can_change_status`, вычисленный серверной функцией `nav_v2_can_change_task_status`.
2. `nav_v2_get_deal_card_lite` возвращает id, заголовок, описание, статус, приоритет, роль и срок, но не возвращает `can_change_status`.
3. `task-action-guard-v2.js` повторно загружал lite DTO и преобразовывал отсутствующее разрешение в `false`.
4. В результате guard блокировал действие даже тогда, когда полная карточка уже получила разрешение от сервера.

Это объясняет отсутствие реальных переходов после появления кнопок lifecycle.

## Решение

Полная карточка публикует memory-only snapshot разрешений до отрисовки рабочих действий.

Snapshot содержит только:

- id сделки;
- id задачи;
- статус;
- назначенную роль;
- версию task contract и outcome state, если они есть;
- точные серверные permission booleans.

Не передаются:

- ФИО, email и телефон;
- адрес сделки;
- заголовок и описание задачи;
- `assigned_to`;
- документы, комментарии и другие клиентские данные.

Guard объединяет lite DTO с разрешениями полной карточки только при совпадении id сделки. Он не выводит право из роли, назначения или содержимого задачи.

## Fail-closed

Если полной карточки нет, snapshot повреждён или относится к другой сделке, разрешение не восстанавливается. Действие остаётся заблокированным.

Ошибка lite-запроса не блокирует карточку, если в памяти уже есть точный серверный snapshot полной карточки. При этом никакое новое разрешение не вычисляется на клиенте.

## Базовая карточка

`deal-card-v2.js` больше не определяет право по локальной роли и `assigned_to`. Кнопки создаются только при точном `task.can_change_status = true`, который пришёл из полной серверной карточки.

## Заблокированный follow-up

Добавление `can_change_status` непосредственно в production-функцию `nav_v2_get_deal_card_lite` остаётся предпочтительным упрощением контракта, но требует отдельного разрешения на production database change.

Этот follow-up не блокирует frontend-исправление, поскольку источник разрешения уже существует в действующей полной карточке.

## Границы

Не выполнялись:

- production DDL или DML;
- миграции, backfill или массовое изменение задач;
- изменение RLS, grants, Auth или Edge;
- новый RPC;
- browser storage или telemetry;
- автоматический переход задачи;
- изменения `leader_*`.

Production Supabase не менялся.
