# Navigator v2 — восстановление серверных разрешений задач

## Проблема

После включения lifecycle `open → in_progress → результат → done` production оставался в состоянии:

- 98 задач;
- 88 задач `open`;
- 0 задач `in_progress`;
- 0 задач `done`;
- 0 событий `task_status_changed`.

Read-only проверка действующих функций показала конкретный разрыв:

1. `nav_v2_get_deal_card` возвращает для каждой задачи авторитетный `can_change_status`, вычисленный серверной функцией `nav_v2_can_change_task_status`.
2. `nav_v2_get_deal_card_lite` возвращает данные задачи, но не возвращает `can_change_status`.
3. `task-action-guard-v2.js` загружал lite DTO и преобразовывал отсутствующее разрешение в `false`.
4. Guard блокировал действие даже тогда, когда полная карточка уже получила разрешение от сервера.

Это объясняет отсутствие реальных переходов после появления lifecycle-кнопок.

## Решение

Guard продолжает использовать `nav_v2_get_deal_card_lite` как быстрый источник статуса и метаданных задачи.

Если хотя бы у одной задачи отсутствует авторитетное permission-поле, guard получает разрешения из уже действующего `nav_v2_get_deal_card` и объединяет только:

- `can_change_status`;
- bounded permission booleans;
- версию task contract и outcome state;
- актуальный статус и назначенную роль.

Право не вычисляется на клиенте по роли, названию, источнику или назначению.

Полная карточка входит в существующий `DEDUPED_RPC_NAMES`, поэтому одновременная загрузка основной карточки и guard использует один in-flight запрос, а не создаёт второй одинаковый сетевой вызов.

## Fail-closed и восстановление

- Явный серверный отказ остаётся отказом.
- Если lite DTO недоступен, guard может восстановить работу из полной карточки.
- Если недоступны оба источника, все действия остаются заблокированными и пользователь получает понятную ошибку.
- Bounded transport остаётся выключенным.
- Никакие задачи не переводятся автоматически.

## Заблокированный follow-up

Добавление `can_change_status` непосредственно в production-функцию `nav_v2_get_deal_card_lite` остаётся предпочтительным упрощением контракта, но требует отдельного разрешения на production database change.

Этот follow-up не блокирует frontend-исправление, поскольку авторитетный источник разрешения уже существует в полной карточке.

## Границы

Не выполнялись:

- production DDL или DML;
- миграции, backfill или массовое изменение задач;
- изменение RLS, grants, Auth или Edge;
- новый RPC;
- browser storage или telemetry;
- автоматический переход задачи;
- изменения `leader_*`.

Production Supabase не менялся.
