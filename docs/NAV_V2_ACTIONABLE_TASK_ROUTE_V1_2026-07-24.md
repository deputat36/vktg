# Navigator v2 — маршрут к исполнимой задаче

## Результат проверки предыдущего этапа

Permission fallback из PR #497 присутствует в `main`, его desktop/mobile проверки зелёные. Production после публикации по-прежнему содержит 88 открытых задач, 0 задач в работе, 0 завершённых задач и 0 событий `task_status_changed`.

Повторный анализ не выявил возврата прежней ошибки permission DTO. Следующее препятствие находилось в существующем блоке «Главное действие сейчас».

## Подтверждённая проблема

Блок выбирал самую срочную открытую задачу независимо от того, может ли текущий пользователь выполнить её.

Read-only анализ действующих назначений показал:

- у СПН найдено 6 доступных связок «пользователь–сделка» с открытыми задачами;
- во всех 6 связках у СПН есть как минимум одна исполнимая задача;
- во всех 6 случаях прежний алгоритм выбирал задачей №1 более срочную задачу другой роли;
- у юриста 13 из 17 доступных связок содержат исполнимую задачу, ещё 4 остаются только контрольными.

Из-за этого пользователь открывал карточку, видел чужую задачу как главное действие и не получал прямого маршрута к собственной работе.

## Что изменено

В существующем блоке, без нового экрана:

1. Сначала выбирается открытая задача с серверным `can_change_status=true` для текущего пользователя.
2. Среди исполнимых задач сохраняется прежний приоритет по просрочке, важности и статусу «в работе».
3. Если исполнимых задач нет, блок по-прежнему показывает самую важную задачу для контроля.
4. Для открытой исполнимой задачи кнопка называется «Начать эту задачу».
5. Для задачи в работе кнопка называется «Продолжить и завершить».
6. После нажатия открывается существующая вкладка «Задачи», прокручивается нужная задача и фокус устанавливается на разрешённую рабочую кнопку.
7. Чужая задача остаётся видимой для контроля, но не перехватывает главное действие.

## Проверка

Добавлена browser-проверка реальной страницы карточки сделки:

- более срочная задача принадлежит юристу;
- менее срочная задача принадлежит текущему СПН и разрешена сервером;
- блок выбирает задачу СПН;
- кнопка открывает вкладку «Задачи»;
- фокус попадает на «Начать работу»;
- выполняется точный переход `open → in_progress` через существующий RPC;
- дополнительный обработчик или новый экран не создаётся.

Проверка выполняется на desktop и mobile.

## Границы

- production Supabase schema/data/Auth/RLS/grants/Edge не меняются;
- задачи автоматически не переводятся и не закрываются;
- назначения и сроки не меняются;
- bounded transport остаётся выключенным;
- `leader_*` не затрагивается.

## Следующее наблюдение

После публикации нужно проверять первые реальные `in_progress`, `done`, `task_status_changed` и result-комментарии. Если переходы по-прежнему не появятся, следующий repository-only этап — проверить вход пользователей в конкретные сделки из рабочего стола и роль-фильтры списка сделок, не создавая отдельный task screen.
