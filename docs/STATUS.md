## Актуально на 19 октября 2026 — помощник подготовки

Последнее прямое задание владельца заменяет прежнюю концепцию диспетчера сделок. Реализуется независимый модуль `preparation.html` в том же репозитории: три цели, адаптивные вопросы, источники фактов, ориентир документов, конкретный следующий шаг и копируемый запрос. Ответы только в памяти страницы; ПД, клиентской базы, договоров, чата, задач и юридического допуска нет.

Концепция и альтернативы: `PREPARATION_HELPER_CONCEPT.md`; требования/аудит: `PREPARATION_HELPER_REQUIREMENTS.md`; приёмка: `PREPARATION_HELPER_ACCEPTANCE.md`. Правила редактируются через проект JSON и PR, а не прямой записью на сайт. Production Supabase и чужие проекты не меняются. Старый v2 сохранён, его миграция и юридические gates требуют отдельного решения.

Предыдущие пункты ниже — история разработки, не backlog новой концепции.

## Актуально на 18 июля 2026 — governed save boundary новой анкеты

- Добавлен repository-only private ledger contract: request UUID связан с verified actor и fingerprint, exact completed replay возвращает stored result, changed actor/payload отклоняется.
- Deferred constraint запрещает commit `started`, поэтому claim, owner/side-aware business rows и completion обязаны выполняться в одной транзакции.
- Новый write plan заменяет только три архитектурных legacy STOP в harness: отсутствие ledger, generic seller/buyer documents и неявный current actor. Client owner IDs не принимаются.
- Все 12 неподдержанных legacy semantic rules остаются fail-closed; production migration, public RPC и deployment отсутствуют.
- PostgreSQL 17 workflow проверяет seller-only rows, manager→lead assignment, exact replay, две конкурентные сессии, failure-after-rows rollback/retry и полный layered rollback.
- Production Supabase не изменён.

## Актуально на 18 июля 2026 — integration contract сохранения intake

- Добавлена pure repository-only цепочка `recompute → allowlist → sanitize → legacy save mock` с обязательным UUID request ID и отдельным trusted server context.
- Client owner IDs, произвольные верхнеуровневые поля и client passport/work-plan preview не проходят в legacy payload; legal passport и work plan вычисляются заново.
- Server owner-resolution показывает только preview: без назначенного lawyer/broker роль остаётся unresolved, реальные задачи не создаются.
- Exact production snapshot выявляет три STOP-фактора: нет request ledger, legacy создаёт generic документы обеих сторон и назначает текущего actor вместо подтверждённого lead SPN.
- Из 25 canonical rules 13 имеют точную legacy projection, 12 зафиксированы как явные semantic gaps. Production call всегда выключен.
- PostgreSQL 17 harness доказывает exact replay/recovery, отказ при changed payload, один mock business write, privacy allowlist и полный rollback. Production Supabase не изменён.

## Актуально на 18 июля 2026 — server adapter новой анкеты

- Добавлен repository-only SQL-адаптер, который заново вычисляет 25 intake rules, маршрут специалистов, юридический паспорт, side-aware документы, task candidates и gates из канонического каталога.
- Клиентские `legal_passport` и `intake_work_plan` не считаются доверенными: серверная функция заменяет их расчётом из allowlisted draft и отклоняет неизвестные, персональные, банковские, паспортные и документные поля.
- Брокерский маршрут ограничен обычной и военной ипотекой; client draft не может создать назначенную задачу, пока server workflow не подтвердит конкретного участника сделки.
- Detached PostgreSQL 17 harness проверяет 13 позитивных и негативных сценариев, private ACL, отсутствие DML и полный rollback функций.
- Прототип не находится в migrations, не подключён к save RPC и не содержит production project ref или credentials. Production Supabase и рабочие данные не изменены.

## Актуально на 17 июля 2026 — side-aware work plan новой анкеты

- Pure work-plan model формирует документы только из matched rules и только для сопровождаемой стороны; объектные и общесделочные документы остаются допустимыми независимо от стороны.
- Для партнёрской сделки сторона не угадывается: side-specific документ остаётся в `skipped_documents`, пока явно не задана сопровождаемая сторона.
- Каждый task candidate содержит owner role/id, действие, deadline rule, evidence, ожидаемый результат и влияние на gates. Без конкретного owner id кандидат не попадает в `ready_tasks`.
- Брокерские задачи по-прежнему возможны только для обычной и военной ипотеки; при ипотеке с маткапиталом юридическая и ипотечная части разделены.
- Detached трёхэтапный экран показывает side-aware документы и конкретные задачи, не загружает файлы и не отправляет mutations. Production Supabase не изменён.

## Актуально на 17 июля 2026 — первый экран юридического паспорта

- Юрист первым видит конкретный запрос, ожидаемое решение, срок, объект, сопровождение и СПН по сторонам, а не общий процент готовности.
- Факты разделены на подтверждённые документом, сообщённые клиентом и неизвестные; рядом показаны стоп-факторы, четыре статуса документов, расчёты, расходы, задаток и следующий шаг СПН.
- Кнопки `можно дальше / нужна информация / нужны документы / стоп-фактор` используют существующий юридический action lifecycle и не создают нового mutation transport.
- Старые сделки без паспорта v1 получают честный legacy fallback: экран не придумывает evidence и явно сообщает, что источник фактов не разделён.
- Модель pure, view использует только уже загруженный payload, не вызывает RPC/fetch и не хранит данные в browser storage. Desktop/mobile regression проверяет порядок первого экрана, действия и отсутствие лишних запросов.

## Актуально на 17 июля 2026 — detached трёхэтапный прототип анкеты

- Добавлен отдельный `spn-intake-prototype-v2.html`: три верхнеуровневых этапа, одна primary action, четыре состояния факта и отдельный источник информации.
- Экран восстанавливает локальный черновик после reload, не очищает скрытые ответы и формирует preview юридического паспорта и трёх gates.
- Передача юристу требует подтверждения конкретного запроса и ожидаемого решения; обязательные документы получают безопасные статусы без загрузки файлов.
- Брокерская кнопка появляется только при обычной или военной ипотеке. Маткапитал без ипотеки остаётся маршрутом СПН/юриста.
- Прототип не импортирует Supabase, не вызывает RPC и не отправляет `POST/PUT/PATCH/DELETE`. Desktop и mobile browser regression закрепляет zero-mutation, reload recovery и отсутствие горизонтального переполнения.

## Актуально на 17 июля 2026 — безопасное восстановление после неопределённого сохранения

- Мастер СПН больше не считает сделку найденной только по совпадению типа объекта после тайм-аута сохранения.

- Для legacy DTO без серверного признака автора сохраняется более строгий fallback: требуется точное совпадение адреса, типа объекта и режима подготовки.
- Если безопасно подтвердить созданную карточку нельзя, мастер оставляет черновик и предлагает проверить список сделок вместо открытия возможной чужой или старой карточки.
- Production Supabase, RPC, schema, Auth, RLS, grants и рабочие данные не изменены.

## Актуально на 15 июля 2026 — мобильный операционный первый экран

- Срез использует уже загруженные payload, не добавляет RPC, migrations, grants, browser storage или production mutations.

## Актуально на 15 июля 2026 — подтверждение результата и следующий шаг

- Карточка показывает недавний серверно подтверждённый результат после завершения задачи, проверки документа, устранения риска или перехода сделки на следующий этап.
- Подтверждение строится только когда audit event совпадает с текущим состоянием сущности; отменённые, повторно открытые, no-op и старше семи дней события не выдаются за выполненный результат.
- Пользователь видит, что изменилось, кто зафиксировал результат, время и понятный серверный факт без названий таблиц или RPC.
- Тот же pure action-first расчёт автоматически выбирает следующее действие, ответственного, срок, критерий результата и точный раздел карточки.
- Hook использует уже загруженные `events`, `tasks`, `documents`, `risks` и `deal`; новых RPC, migrations, grants и production mutations нет.

## Актуально на 15 июля 2026 — единый документный цикл юриста

- В карточке юриста появился единый маршрут `нужен → запрошен → получен → проверен / проблема` поверх уже загруженных `documents`, `participants` и `events`.
- Pure-модель выбирает один приоритетный документ: сначала проблема, затем полученный для проверки, просроченный запрос и обязательные документы к задатку/сделке.
- Для документа показаны сторона, причина, влияние на задаток/сделку, ответственный, контрольный срок, последнее изменение, проблема или комментарий и одно следующее действие.
- Статус меняется существующим `nav_v2_update_document_workflow`; RPC сохраняет заметку и audit event. После reload карточка показывает серверное подтверждение и автоматически выбирает следующий документ.
- Кабинет юриста ведёт очереди проблемных, просроченных и ожидаемых документов прямо в новый цикл. Новых RPC, migrations и production mutations при публикации нет.

## Актуально на 15 июля 2026 — единый цикл доработки СПН

- Карточка показывает один маршрут `замечание → раздел исправления → сохранение → повторная отправка → подтверждение` поверх уже загруженного payload.
- СПН видит автора и причину возврата, структурированный список замечаний, прямой переход в данные сторон, документы, расчёты, расходы, риски, задачи, ответственность или комментарии.
- Состояние `исправлено / не исправлено` показывается только для пунктов, которые можно проверить по текущим данным карточки; неподтверждаемые пункты не угадываются.
- Повторная отправка требует содержательного комментария о выполненных исправлениях и после reload показывает серверное событие, получателя, новый статус, следующего ответственного, срок и дальнейшее действие.
- Юрист и менеджер формируют структурированный возврат через существующий `nav_v2_return_spn_rework`; СПН отправляет результат через существующий `nav_v2_submit_spn_rework`.
- Новых RPC, migrations, grants и production mutations нет. Три конкурирующих rework entry-модуля заменены одним explicit lifecycle hook без повторной загрузки карточки.

## Оставшиеся риски и технический долг

- Supabase advisor продолжает показывать предупреждения по части `SECURITY DEFINER` функций, доступных authenticated. Часть ожидаема, но нужен пофункциональный аудит каждой RPC.
- В advisor есть предупреждение по `leader_public_lead_audit`; это зона CRM «Лидер», не Навигатора.
- В Supabase Auth выключена leaked password protection. Желательно включить в настройках Auth.
- Фронтенд v2 местами построен слоями дополнительных JS-модулей. Следующая стабилизация должна упростить карточку сделки и убрать лишние модульные накладки.
- Документам нужен полноценный worklist/kanban с фильтрами по ответственному, сроку, статусу и просрочке.
- Кабинету юриста нужен отдельный фильтр/очередь по блокирующим решениям, если команда начнет активно пользоваться review-слоем.
- GitHub raw/curl и clone из терминала в этой среде возвращают 403, поэтому чтение/запись репозитория выполняется через GitHub-коннектор.
- Changelog Supabase из терминала возвращает 403; при Supabase-работах используется MCP-проверка текущей схемы и smoke-тесты.
